2. Whose fault? — compare two bars

The single most valuable diagnostic on this page.

CASE A - the SERVER is slow
  duration   ####################  8.25s
  waiting    ###################   8.24s   <-- same length
                                            => REAL FINDING. Escalate.

CASE B - YOUR MACHINE is slow        (the real 250-VU MainManager run)
  duration   ####################  44s
  waiting    #                     0.5s    <-- tiny!
  receiving  ###################   42s     <-- the gap lives HERE
                                            => YOUR RIG. Do not blame the product.
Same total duration, opposite conclusion. Reporting Case B as a product defect would have blamed the wrong team.

4. Why a percentile can miss a problem

 sorted fastest ---------------------------------------------> slowest
 [######################################---------]
  1                                    95 96    100
                                        ^         ^
                                       p95       max

  p95 catches problems bigger than  5%
  p99 catches problems bigger than  1%

  Only 5 of 100 slow?  ->  p95 reads "fine". ONLY p99 finds it.

5. Bimodal — when a percentile invents a number

 requests
    |  ____                                      __
    | ######                                    ####
    |########                                  ######
    +---+-----------------+--------------------+--->  response time
      250ms            p90 = 2.65s           8.25s
    FAST PATH              ^                SLOW PATH
      (90%)          NOTHING HERE!            (10%)

  p90 landed in the GAP -> a value NO request took
  => Report the two groups: "90% at 0.25s, 10% at 8s"

6. Sizing — Little's Law, both directions

        ==========================================
          VUs  =  throughput  x  iteration_duration
        ==========================================

  PLANNING (solve for VUs)          READING (solve for throughput)
  ------------------------          ------------------------------
  target      20 req/s              measured   5 VUs, 2.5s iteration
    / 2 requests per journey           throughput = 5 / 2.5
    = 10 journeys/s   <-- THE TRAP               = 2 journeys/s
    x 2.5s
    = 25 VUs

  Where 2.5s comes from:  1-VU SMOKE TEST -> iteration_duration (med, not avg)
The trap: convert requests/s to journeys/s BEFORE multiplying. Skip it and you size the test 2x or 10x wrong.

7. A ramp is half a hold

   RAMPED                                 HELD
 VUs                                    VUs
  5|      +-----------+                  5|--------------------
   |     /|           |\                  |
   |    / |   RECT     | \                |    RECTANGLE only
  0|  /TRI|           |TRI\              0|
   +------------------------->             +-------------------->
   0   10s         30s    40s              0                  40s

  area = 25 + 100 + 25 = 150             area = 5 x 40 = 200
  iterations = 150 / 1.25 = 120          iterations = 200 / 1.25 = 160

  total iterations = AREA under the VU curve / iteration_duration

8. Report the plateau, not the average

 req/s
  4|        +-----------+       <-- 4.07 /s  = the REAL test load   [correct]
   |       /             \
  3| - - - - - - - - - - - - -  <-- 3.06 /s  = the run AVERAGE      [misleading]
   |     /                 \
  0|   /                     \
   +------------------------------->
     ramp      plateau      ramp
A summary cannot show you where the plateau was — you have to calculate it, or graph it. This is one of the main reasons for the Grafana week.

10. Script structure — when each part runs

 TIME ------------------------------------------------------------>

 init        #  #  #  #                                #  #
             +-- MANY times. Cheap. No side effects. No HTTP. --+

 setup()        #
                +-- ONCE. Tokens, test data, expensive setup.

 VU code           ############################
                   +-- EVERY iteration. x thousands.

 teardown()                                           #
                                                      +-- ONCE. Cleanup.

   Ask of every line:  "ONCE, or EVERY TIME?"
   Wrong answer  =>  the login-flood bug

13. Reporting — data into decision

   RAW DATA                           THE REPORT
 +---------------+
 | p95 = 8.25s   |--+   +------------------------------------------+
 | 10% slow      |  |   | 1  VERDICT   "failing our 3s target"     |
 | endpoint X    |  +-->| 2  NUMBER    "p95 = 8.25s vs 3s target"  |
 | 4.13 req/s    |  |   | 3  HUMANS    "1 in 10 waits 8+ seconds"  |
 | 0 http failed |  |   | 4  WHERE     "isolated to endpoint X"    |
 +---------------+  +-->| 5  THE ASK   "profile that call"         |
                        +------------------------------------------+

              Never lead with the good news.

The 6 sentences that carry most of it

1.  Open model = fixed load;  closed model = fixed workers.
2.  VUs = throughput x iteration_duration.
3.  Report p95, never avg.
4.  duration ~ waiting -> the product.  duration >> waiting -> my rig.
5.  Green status codes are not a passing test.
6.  Checks + thresholds, or the report is decoration.
