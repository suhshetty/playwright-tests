k6 Summary – One Page Reference Card

Performance testing quick reference · keep beside the terminal

THE TIMELINE – memorise this one sentence, derive the rest

A request waits to start, connects, encrypts, sends, waits for the server, then downloads.

blocked  →  connecting  →  tls_handshaking  →  sending  →  waiting  →  receiving
|------------- setup (NOT in duration) -------------|  |------ http_req_duration ------|

READING ORDER – four numbers give you a verdict

#Look atQuestion it answers
1http_req_failedDid it even work? If high, nothing else matters.
2http_req_duration p95Is it fast enough? (This is what you report.)
3http_req_waiting p95Is the SERVER the cause — or my test rig?
4http_reqs/sAt what load did I prove this?

THE THREE REFLEX COMPARISONS

If you seeConclude
duration approx equal to waitingThe server is genuinely slow. Real finding — escalate.
duration much greater than waitingCheck receiving. Probably your load generator, not the product.
avg greater than medA tail exists. Go look at p95, p99, max.

METRICS BY PRIORITY

MetricTierThe one thing it tells you
http_req_waiting1How slow the server really is (TTFB). The truest server measure.
http_req_duration1Total request time = sending + waiting + receiving. What you report as latency.
http_req_failed1Share of requests with a non-2xx/3xx status. NOT whether the business action worked.
http_reqs1Total requests + per-second rate = throughput.
iterations1Completed journeys, TOTAL across all VUs (not per VU).
iteration_duration1One full journey incl. your sleep. Use for SIZING, never for server speed.
http_req_receiving2Body download time. High = big payloads or a strained generator.
http_req_blocked2Pre-request wait (DNS + connect + TLS + free-connection wait). Non-zero on MOST requests = connections not being reused.
{ expected_response:true }2Same duration metric, successful responses only. Use when failures exist — fast errors drag avg down and fake good latency.
http_req_connecting3TCP connect only. Mostly measures distance to the server.
http_req_tls_handshaking3HTTPS encryption setup. Expensive but paid once per connection.
http_req_sending3Pushing request bytes out. Negligible unless uploading.
data_received / data_sent3Total bytes + rate. Useful for spotting oversized payloads.
vus / vus_max3Active / allocated VUs. vus is a time SAMPLE, not a total — a low min just means VUs had finished.

STATISTICS – which number to trust

StatMeansUse it for
minFastest single requestBest-case reference only.
med (p50)Middle value when sortedThe typical experience. Hides the tail completely.
avgSum ÷ countNever report it. Only useful compared against med to detect a tail.
p(95)95% finished within thisThe standard SLA target. This is what you report.
p(99)99% finished within thisCatches problems affecting 1–5% of requests, which p95 misses.
maxSlowest single requestContext only. Too noisy to set a target against.
A percentile is a POSITION, not a group: position = % × total requests. p95 is the single value at the 95% mark — a boundary line, not the requests above it.
So a percentile only sees a problem bigger than the slice above it: p95 catches >5% of requests; p99 catches >1%. If exactly 5% are slow, p95 misses them entirely.
Add p99 to any run: summaryTrendStats: ['min','med','avg','p(90)','p(95)','p(99)','max']

SIZING & LOAD

throughput = VUs ÷ iteration_duration          total http_reqs = iterations x requests per iteration

Verify two ways: throughput x duration should equal your iteration estimate.
TrapReality
“We tested with 100 users”Meaningless. Same 100 VUs = 3 or 400 req/s depending on think time. Always state throughput.
More VUs must mean higher latencyNo. Latency stays FLAT until a resource saturates, then climbs steeply at the “knee”.
Fixed VUs apply constant loadNo. When the server slows, VUs wait longer and load DROPS. Closed-model trap — use arrival-rate executors for capacity tests.
Comparing against last week's baselineBaselines drift ~4% for no reason. Re-measure in the same session.

REPORTING – the 5-part sentence

1. Verdict vs target   2. p95 + the target   3. Impact in HUMANS   4. Which feature   5. The ask
RuleDetail
Never lead with good news“95% is fine” makes the manager stop listening.
Convert requests to usersusers affected = 1 - (1 - p)^requests per session. 10% slow requests x 10-request session = 65% of users.
Report the shape, not one numberp50 / p95 / p99 / max together tell a story a single figure cannot.
Bimodal dataIf a percentile shows a value no request took, report the two groups: “10% take 8s, 90% take 0.25s.”

TRAPS THAT PRODUCE FALSE GREEN

TrapWhy it fools you
http_req_failed: 0%Only means status codes were 2xx/3xx. A 200 returning a login page or error body counts as SUCCESS. Use check() on the body.
Reporting avgBlends good and terrible into a number describing nobody. Hides the users who actually suffer.
Fast errorsFailures often return in milliseconds and pull avg down, making a broken system look fast. Read the expected_response:true row.
A summary table aloneCannot distinguish random scatter from a mid-test cliff. Identical avg/p99/max, completely different problems. Use a time-series graph.
