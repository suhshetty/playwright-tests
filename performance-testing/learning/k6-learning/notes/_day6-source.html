Day 6 – Think Time, Pacing and Little's Law

Learning notes · Script: day6-littles-law.js

1. Little's Law — the formula, named

L  =  lambda  x  W          (queueing theory, 1961)

VUs  =  throughput  x  iteration_duration
SymbolMeansIn k6
Lhow many things are in the system at onceVUs
lambdaarrival ratethroughput
Wtime each thing spends insideiteration_duration

Solve for whichever you do not know

VUs        = throughput x iteration_duration      <-- sizing a test (PLANNING)
throughput = VUs / iteration_duration             <-- reading a run
duration   = VUs / throughput                     <-- "how long is a journey?"

2. Think time and pacing are different things

 Think timePacing
What it isa pause between actionsa fixed cadence between iterations
Controlshow long a journey takeshow often a journey starts
In k6sleep()the arrival-rate executor
constant-arrival-rate IS pacing — it starts an iteration every 200ms (at 5/s) whether the previous one has finished or not. That is exactly why it does not sag when the server slows down.

3. The coffee shop — the whole concept in one analogy

The barista makes 5 coffees a minute.

If each customer…People in the shopBarista's work
leaves immediately~25 coffees/min
sits for 1 minute~75 coffees/min
sits for 5 minutes~285 coffees/min

The shop looks empty or packed. The barista does exactly the same work.

"we support 28 concurrent users"  ->  tells you nothing
"we support 5 requests/sec"       ->  tells you everything
When someone says “it must handle 500 users”, your first question is: “Doing what, how often?”

500 users clicking once an hour is almost nothing. 500 users clicking every 2 seconds is ~250 req/s.

4. The experiment

import http from 'k6/http';
import { sleep } from 'k6';

const THINK = __ENV.THINK ? parseFloat(__ENV.THINK) : 1;

export const options = {
  scenarios: {
    fixed_rate: {
      executor: 'constant-arrival-rate',
      rate: 5, timeUnit: '1s', duration: '30s',
      preAllocatedVUs: 5,
      maxVUs: 100,
    },
  },
};

export default function () {
  http.get('https://quickpizza.grafana.com/');
  sleep(THINK);
}

Run three times with the same rate and only the think time changed:

k6 run -e THINK=0 ...    k6 run -e THINK=1 ...    k6 run -e THINK=5 ...

Note: the file never changes. `-e THINK=5` sets __ENV.THINK, which the script reads.

Predicting it without running

iteration_duration = request time + sleep = 0.25s + THINK
VUs                = rate x iteration_duration = 5 x (0.25 + THINK)

vus_max can never be below preAllocatedVUs. And the 0.25s is measured — it is the QuickPizza homepage request time from the Day 1 smoke test, re-confirmed on every day since (246 / 257 / 249 / 245 / 254 ms).

Unit reminder: 254ms / 1000 = 0.254s. Little's Law needs seconds, because the rate is per second.

5. Results

THINK=05–77 correct4.922

THE PROOF — the headline result

THINK=0   http_req_duration  med = 253.64ms      (7 VUs)
THINK=1   http_req_duration  med = 252.72ms     (16 VUs)
THINK=5   http_req_duration  med = 252.62ms     (28 VUs)
Within 1 millisecond of each other, across runs with 4x different VU counts.

The VU count changed 4x. The server did not notice. Because the RATE of requests never changed — only how long each user rested in between.

VU count is not load. Throughput is load.

6. Why THINK=1 overshot to 16 VUs

http_req_blocked         max = 4.00s
http_req_tls_handshaking max = 3.77s
iteration_duration       max = 5.25s   (vs med 1.25s)

A few TLS handshakes took about 4 seconds. During that stall k6 hired extra VUs to defend the rate — and vus_max is a high-water mark, so it never comes back down.

Little's Law predicts the STEADY-STATE need. vus_max reports the WORST MOMENT.

They agree on a clean run (THINK=5: predicted 27, actual 28). They diverge when something transient stalls the test.

7. The bonus lesson — the throughput sag was YOUR rig, not the server

target 5/s     THINK=0: 4.92     THINK=1: 4.48     THINK=5: 3.63
dropped:                    2                11                23

Cause: preAllocatedVUs: 5 was under-provisioned.

THINK=0  needs ~2 VUs   ->  5 ready  ->  plenty        ->   2 drops
THINK=1  needs ~7 VUs   ->  5 ready  ->  short         ->  11 drops
THINK=5  needs ~27 VUs  ->  5 ready  ->  VERY short    ->  23 drops

k6 can recruit up to maxVUs: 100, but not instantly. While it was hiring, scheduled iterations missed their slots.

dropped_iterations does NOT automatically mean the server could not cope. Check your own provisioning first.

Reporting “the system only sustained 3.63 of 5 req/s” here would have blamed the server for a test-configuration mistake — exactly the artefact-vs-defect distinction from Day 4, met again in the wild.
The rule: 
preAllocatedVUs = your Little's Law calculation     (not a guess)
maxVUs          = 3-5x that                        (headroom)

8. Day 6 cheat sheet

SituationWhat to do / remember
Someone says “support 500 users”Ask “doing what, how often?” Convert to req/s.
Sizing a testVUs = req/s ÷ requests-per-iteration × iteration_duration
Setting preAllocatedVUsUse the Little's Law figure, not a guess.
Setting maxVUs3–5× preAllocatedVUs.
vus_max far above your calculationLook for a transient stall (TLS, cold start). It is a high-water mark.
dropped_iterations presentCheck preAllocatedVUs BEFORE blaming the server.
Comparing runs with different think timesCompare http_req_duration, not VU count.
Reporting concurrencyState req/s. VU count alone is meaningless.

9. Day 6 in three lines

1.  Think time changes how many VUs you need - not how hard the server works.
2.  VUs = req/s x journey length.   (Little's Law)
3.  "N users" is meaningless. Always state requests/sec.
