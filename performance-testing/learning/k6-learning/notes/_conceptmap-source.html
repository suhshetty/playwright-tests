k6 Concept Map

How VUs, iterations, requests, throughput and latency relate to each other

1. The vocabulary, as a factory

VU                  =  a worker
iteration           =  one complete task the worker does
iteration_duration  =  how long one task takes
requests            =  the individual steps inside a task
throughput          =  tasks finished per second by the WHOLE team
latency             =  how long the SERVER takes to answer one step

2. One VU over time

time ->  0s                    2.55s                   5.1s
         |                       |                       |
VU 1     [ req  sleep  req  sleep ][ req  sleep  req  sleep ]
         |----- 1 iteration ------||----- 1 iteration ------|
                 2.55s                     2.55s
               2 requests                2 requests

One worker finishes a task every 2.55s, which is 1 / 2.55 = 0.39 tasks per second.

3. More VUs work in PARALLEL

time ->  0s              2.55s            5.1s
         |                 |                |
VU 1     [-- iteration --][-- iteration --]
VU 2     [-- iteration --][-- iteration --]
VU 3     [-- iteration --][-- iteration --]
VU 4     [-- iteration --][-- iteration --]
VU 5     [-- iteration --][-- iteration --]
         |-------+--------|
                 |
         5 tasks done in 2.55s  =  1.96 tasks/sec
More workers = more throughput. The task duration itself does not change (until the server saturates — see section 7).

6. The single relationship to hold in your head

                          VUs
        throughput  =  ---------------------
                       iteration_duration

Everything else is that, multiplied by something:

Multiply throughput by……to get
durationtotal iterations
requests per iterationrequests per second
bothtotal requests
Rearranged for planning: VUs = target journeys/s × iteration_duration

The one trap: convert the target from requests/s to journeys/s FIRST — journeys/s = requests/s ÷ requests per iteration. Skipping this sizes the test 2x or 5x wrong.

7. Latency is a SEPARATE axis

The trap that catches everyone: throughput and latency are independent until the server saturates.

latency
  ^
  |                                       ___/   <-- the KNEE: workers start
  |                                    __/           queueing for the server
  |________________________________ __/
  |   FLAT - server has spare capacity
  +-------------------------------------------> throughput

     adding VUs moves you RIGHT -->
     it does NOT move you UP until you reach the knee
ObservationMeaning
Latency flat as VUs riseYou are on the flat part. Server has spare capacity. Normal and healthy.
Latency starts climbingYou have found the knee. This is the capacity limit.
Latency climbing AND throughput stops risingSaturated. Adding VUs now only adds queueing, not load.

Example: a 1-VU run and a 10-VU run both measured ~258ms. 10x the load, identical latency — because 8 req/s is far to the left of the knee.

8. Where latency fits back into the picture

iteration_duration  =  (sum of all request latencies)  +  (sum of all sleeps)

     e.g.   2.55s   =   0.25s + 0.25s   +   1s + 1s
                        |-- server --|     |-- your think time --|
This closes the loop: when the server slows down, iteration_duration grows, so throughput = VUs / iteration_duration FALLS.

That is the closed-model trap: with fixed VUs, a struggling server receives LESS load, not more. Real users keep arriving regardless. Capacity tests therefore use arrival-rate executors instead of fixed VUs.

10. Journey length drives VU count

For the same target of 10 journeys/sec:

iteration_durationVUs required
1s10
2.55s26
10s100
40s (a full MainManager journey)400

Longer journeys need more VUs for identical throughput. This is why heavy end-to-end scenarios are so expensive to load-test, and why VU count alone never describes a test.
