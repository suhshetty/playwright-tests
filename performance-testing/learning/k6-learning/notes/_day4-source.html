Day 4 – Checks vs Thresholds

Learning notes · Script: day4-checks.js

1. The gap this day closes

http_req_failed: 0.00%     <-- only means the status code was 2xx/3xx
The old hand-written Scenario2.js was fully green while doing nothing: a dead session cookie made every call redirect to the login page, the login page returned 200, so http_req_failed read 0%.

http_req_failed answers “did HTTP work?” — never “did the business action work?”

2. Two tools, constantly confused

 check()thresholds
Question“Was the response correct?”“Does the run pass?”
Looks atone response, right nowthe whole run's metrics
Where it goesinside VU codein options
Fails the test?NO — records it and continuesYES — sets exit code 99
Analogya thermometerthe fever limit that sends you home
The critical surprise: a failing check() does NOT fail your test. That is deliberate — under load you want the test to continue, not abort on one bad response.

So checks alone are not a gate. You need both.

3. Writing checks

import http from 'k6/http';
import { check, sleep } from 'k6';

export default function () {
  const res = http.get('https://quickpizza.grafana.com/');

  check(res, {
    'status is 200':        (r) => r.status === 200,
    'body contains Pizza':  (r) => r.body.includes('Pizza'),
    'faster than 500ms':    (r) => r.timings.duration < 500,
  });

  sleep(1);
}
  • Capture the response into a variable (const res = ...) so you can interrogate it.
  • Each entry is a name and a function returning true/false.
  • Useful response properties: r.status, r.body, r.timings.duration, r.json(), r.headers.

4. The four-run demonstration – the heart of Day 4

Runs 2 and 3 had the IDENTICAL failure and opposite outcomes.

The only difference is whether a threshold exists.
check() detects the problem. threshold makes it matter.

A framework with checks but no thresholds reports failures nobody is forced to act on. defaultThresholds() in lib/mainmanager.js is exactly this mechanism — which is why a bad MainManager run genuinely fails.

5. The big trap: default ✓ does NOT mean the test passed

Run 3 (threshold breached, no abort):   default ✓   <-- ran all 20s
Run 4 (threshold breached, abort):      default ✗   <-- stopped at 6s
The ✓/✗ on the progress line means “did the scenario COMPLETE?”, not “did the test pass?”

Run 3 proved it: default ✓ while breaching a threshold. 
The verdict lives in:      the ERRO line  +  the exit code
The verdict does NOT live in:  the default ✓/✗

6. Exit codes – why any of this matters

0   = success  ->  pipeline goes green
99  = failure  ->  pipeline goes red

CI reads the exit code and nothing else. Jenkins and GitHub Actions never read your summary. Check it on Windows with:

k6 run script.js
echo $LASTEXITCODE

7. Threshold syntax you will actually use

thresholds: {
  // multiple conditions on one metric
  'http_req_duration': ['p(95)<500', 'p(99)<1000', 'max<3000'],

  // rates use 0-1, NOT percentages
  'http_req_failed': ['rate<0.01'],      // under 1%
  'checks':          ['rate>0.99'],      // over 99%

  // count-based
  'http_reqs': ['count>100'],

  // per-endpoint (requires tags)
  'http_req_duration{name:login}':  ['p(95)<2000'],
  'http_req_duration{name:search}': ['p(95)<800'],
},
The per-tag form is the professional one. Different operations deserve different SLAs — a login may take 2s, a search should not. This is what the SLA_WIDGET_P95 / SLA_FILTER_P95 / SLA_TREE_P95 constants do in the real framework.

Common gotcha

MistakeCorrect
A second export const options inside the default functionoptions is top level and declared ONCE. Add thresholds to the existing block. export inside a function is a syntax error.
'http_req_failed': ['rate<1'] meaning 1%Rates are 0–1. 1% is rate<0.01. rate<1 means “under 100%” — almost always true, so a useless gate.

8. Where threshold values come from

SourceVerdict
Agreed SLA with the customerBest
Measured baseline + acceptable degradationGood
Industry norm (e.g. 3s page load)Starting point only
A number you inventedGuarantees an argument you will lose
Real example: the shared dev box logs in at ~22s against a 10s SLA. That threshold was set for a healthy environment, so on that box it fires constantly and gets ignored.

A threshold nobody trusts is worse than no threshold. Re-baseline per environment.

9. abortOnFail – stopping a doomed run early

thresholds: {
  'http_req_duration': [
    { threshold: 'p(95)<100', abortOnFail: true, delayAbortEval: '5s' },
  ],
},
OptionEffect
abortOnFail: trueKill the run as soon as the threshold is breached.
delayAbortEval: '5s'Wait 5s before evaluating, so start-up noise does not trigger it.

Observed result: a duration: '20s' test ended at 6.0s with “3 complete and 1 interrupted iterations”.

The trade-off

Run 3:  16 requests, 64 checks
Run 4:   4 requests, 16 checks    <-- much smaller sample
Good abort candidateBad abort candidate
  • http_req_failed rate>0.5 — half the requests failing
  • Login broken, so nothing else can be tested
  • checks rate<0.5 — the script clearly is not working
  • p(95)<500 — might recover as caches warm
  • A single slow endpoint
  • Anything marginal
Rule: abort on “this test is now worthless”, never on “this is a bit slow”. Practical value: a 2-hour soak that is obviously broken at minute 3 should not burn the remaining 117 minutes of a shared environment.

10. checks vs http_req_failed – which one goes to the manager

The same 16 requests produced:

checks:           75%    <-- 1 in 4 verifications failed
http_req_failed:  0%     <-- no request failed
MetricAnswers
http_req_failed“Did HTTP work?” — infrastructure. Table stakes.
checks“Did the application work?” — the business question.
http_req_failed is the number that lies. Showing http_req_failed: 0% for the old Scenario2.js would have certified a test that never touched the product. 
Lead with:     checks              <-- did the business action work?
Support with:  http_req_failed + p95 latency
Never show:    http_req_failed alone

11. The mirror-image honesty rule

A failing check has two possible causes:

CauseExampleAction
The app is brokenSearch returns no results under loadEscalate to the dev team
The test is brokenAsserting 'Burger' on a pizza siteFix your own script
In the Day 4 runs it was the second one — the check itself was invalid. The honest report is not “75% failure”, it is “my check was wrong”.

Prove it is the app before escalating. Reporting a test bug as a product defect once will cost you credibility with the dev team for months.

Checks make you honest about the application. They demand you be equally honest about your script.
