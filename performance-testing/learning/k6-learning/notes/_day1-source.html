Day 1 – Performance Testing Foundations with k6

Learning notes · k6 v0.55.2 · Practice script: PerformanceTests\k6-learning\day1-smoke.js

1. What performance testing actually is

  • Functional testing asks: “Does it work?” — a yes/no answer about behaviour.
  • Performance testing asks: “Does it still work when reality shows up?” — a question about time and concurrency.
  • The answer is never yes/no. It is always a distribution of response times.
  • A performance test is a controlled experiment: apply a known load to a known system and measure the time it takes.
Core principle: If you don't control the load, or don't know the state of the system, you didn't run a test — you just generated numbers. Numbers you cannot explain are worse than no numbers at all.

Real-world example

On the MainManager shared dev environment, login took about 22 seconds. On the kommunerelease environment the same login took about 3.7 seconds.

  • No functional test would ever flag this. The login worked. It returned HTTP 200. It was simply unusable.
  • That gap is exactly the kind of defect only performance testing finds.

2. The 4 questions every performance test answers

Before writing a single line of code, say out loud which question you are asking. Every performance test is one of these:

#QuestionWhat it means
1Is it fast enough?At the expected load, does response time meet the agreed SLA?
2How much can it take?At what load does the system degrade or break?
3Does it stay healthy over time?Do memory leaks, connection pools or caches rot after several hours?
4Does it recover?After a spike or a failure, does the system come back on its own?

Most poor performance work skips this step and produces a test that answers nothing.

3. The 6 types of performance test

TypeLoad shapeQuestion it answers
Smoke1–2 VUs, short durationDoes my script work? (Not the system.)
LoadExpected peak load, held steadyQ1 — is it fast enough at normal load?
StressPushed beyond expected peakQ2 — where does it start to hurt?
SpikeSudden jump, then sudden dropQ4 — can it survive a surge and recover?
SoakModerate load held for hoursQ3 — memory leaks and slow degradation
BreakpointRamp up steadily until it failsQ2 — the exact capacity limit (the “knee”)
Golden rule: always smoke test first. A 250-VU run against a broken script wastes an hour and produces confident garbage.

6. The request lifecycle – the structure to memorise

Every HTTP request passes through these stages, in this order:

blocked  →  connecting  →  tls_handshaking  →  sending  →  waiting  →  receiving
|________ connection setup _________|          |______ http_req_duration ______|
Critical: http_req_duration does NOT include blocked, connecting or tls_handshaking. That is why iteration_duration max (1.84s) was larger than anything duration reported — the cold-start handshake lives outside duration.

Connecting vs TLS handshaking, in plain words

MetricSimple explanationEveryday comparison
http_req_connectingTime to open the raw network connection (TCP) to the server. Costs one network round-trip, so it mostly measures how far away the server is.Dialling a phone number and waiting for the other person to pick up. Nobody has spoken yet.
http_req_tls_handshakingTime to set up the encryption for HTTPS. The server proves its certificate and both sides agree on encryption keys. Takes several round-trips plus real CPU work — which is why it is much slower.After they pick up, both of you agree on a secret code language so nobody listening in can understand.

Example: why the Day 1 numbers looked the way they did

Iteration 1 — nothing exists yet, so everything must be built:

DNS lookup           ~22ms   |
TCP connect          2.42ms  |--- all of this = http_req_blocked (597ms)
TLS handshake         572ms  |
send + wait + receive 247ms  ---- http_req_duration
                     -------
total                 ~1.84s  (with sleep(1))  <-- the max iteration_duration

Iterations 2 to 24 — the connection is still open, so go straight to sending:

blocked                  0s   <-- nothing to set up, reuse the open connection
connecting               0s
TLS handshake            0s
send + wait + receive ~246ms
                      ------
total                 ~1.24s  <-- the median iteration_duration

This is why the setup metrics show med = 0s: k6 keeps the connection open and reuses it (HTTP keep-alive), exactly like a real browser.

7. The three diagnostic metrics – who is to blame?

These three tell you which team owns the problem. This is the most valuable diagnostic skill from Day 1.

What you seeWhat it meansWhose problem
waiting is highThe server itself is slow to produce an answer.Application / backend team. A genuine finding — escalate it.
receiving is highBytes are moving slowly. Either huge payloads, or your load generator cannot download them fast enough.Often your own test machine.
blocked is highConnection starvation or slow DNS. If it is non-zero on most requests, connections are not being reused.Usually your rig or an infrastructure limit, not application code.
Real case from the MainManager framework: the 250-VU runs showed a frightening 44–60 second http_req_duration tail. Almost all of it was http_req_receiving, while http_req_waiting stayed at a healthy p95 of about 0.5s. The cause was a single Windows machine unable to download response bodies for 250 VUs — not a product defect. Reporting duration there would have blamed the wrong team.

Which metric answers “how fast is the server?”

  1. http_req_waiting — the truest measure of server speed.
  2. http_req_duration — good, unless payloads are large or the generator is strained.
  3. iteration_duration — never. It contains your own think time.

Proof, using the Day 1 numbers:

iteration_duration    1.27s
http_req_duration   - 0.246s
                    --------
                     ~1.02s   <-- this is just your own sleep(1)

About 80% of iteration_duration was a number you invented. Change sleep(1) to sleep(5) and it becomes ~5.25s while the server does exactly the same work at the same speed. A metric you can move without touching the system cannot measure the system.

However, do not discard iteration_duration — it is how you size a test later (Little's Law, Day 6).

8. Latency statistics – min, med, avg, p90, p95, max

The Day 1 latency line:

http_req_duration: avg=246.37ms  min=244.83ms  med=246.38ms
                   max=247.47ms  p(90)=247.28ms  p(95)=247.44ms
StatisticDefinitionRead it as a sentence
minThe fastest single request“The luckiest request took 244.83ms.”
med (median)The middle value once all times are sorted“Half the requests were faster than 246.38ms, half were slower.”
avgSum of all times divided by the number of requests“The arithmetic mean was 246.37ms.”
p(90)90th percentile“90% of requests finished within 247.28ms.”
p(95)95th percentile“95% of requests finished within 247.44ms.”
maxThe slowest single request“The unluckiest request took 247.47ms.”

How a percentile is actually calculated

Sort every response time from fastest to slowest, then point at the value that sits at that position in the list.

Example with 10 requests:

sorted:  100  110  120  130  140  150  160  170  180  900
                                                  ^     ^
                                                p(90)  max

p(90) = 180ms  → 9 out of 10 requests finished in 180ms or less
max   = 900ms  → one single unlucky request
avg   = 216ms  → a number that no actual request took

Notice that p(90) ignores the single 900ms outlier, while max is defined entirely by it. That is the value of percentiles: they show the bulk of the pain without being hijacked by one freak result.

Median vs average – why both exist

5 requests:  100ms, 100ms, 100ms, 100ms, 10000ms

avg = 10400 / 5 = 2,080ms   <-- destroyed by the one bad request
med =              100ms    <-- unaffected by it
StatisticReacts to extreme values?
avgYes — a single 10-second request drags it up.
medNo — it only cares which value sits in the middle.

9. Why averages lie – and what to report instead

This is the single most important idea in performance testing. Worked example, 100 requests:

 90 requests10 requests
Response time200ms8,000ms
avg  =   980ms   → "about a second, acceptable I suppose"
med  =   200ms   → "200ms, we are fast!"
p95  = 8,000ms   → "1 in 10 users waits 8 SECONDS"   <-- the truth
max  = 8,000ms

Same data. Three completely different stories.

  • avg lies because it blends the good and the terrible into a number that describes nobody's real experience. No user waited 980ms.
  • med lies by omission. It says the typical user is fine and tells you nothing about the other half. The 10 furious users are invisible.
  • p95 tells the truth. It is the worst experience your users routinely hit.
  • max is one unlucky request — a garbage-collection pause or a network blip. Useful as context, too noisy to be the headline.
The rule: Averages hide pain; percentiles expose it. Your users never experience an average — each one experiences a single request. The slow ones are the people who raise tickets, abandon the page and tell your manager the system is slow.

Report to a manager: p95 latency + throughput + error rate. Mention max as context. Never lead with avg.

Industry convention:

  • p50 (median) — the typical experience
  • p95 — the standard SLA target
  • p99 — where the ugliest tail lives; used for critical systems

This is why every SLA in lib\mainmanager.js is a p95 threshold (SLA_WIDGET_P95, SLA_FILTER_P95, SLA_TREE_P95).

Why the Day 1 statistics were all within 3ms of each other

Because there was no variation to measure:

  • 1 VU → no competition for server resources
  • The same request 24 times → identical work every time
  • An idle server → no queueing, no contention
  • A warm cache after request 1 → no cold-path surprises

When there is no spread, every statistic collapses to the same number — avg, med, p95 and max all agree because there is nothing to disagree about.

What creates spread? Load: many VUs queueing for the same CPU, database connection or thread pool; garbage-collection pauses; database lock contention; cache misses; retries and timeouts. None of these exist at 1 VU.

The sting: a beautifully tight 246ms is not good news about the system. It is evidence that no real load was applied.

10. Throughput vs latency

Two different questions, and you always need both:

 Question it answersDay 1 value
LatencyHow long does one request take?246ms
ThroughputHow many requests are handled per second?0.786 requests/sec

Everyday comparison: at a toll booth, throughput is how many cars pass per minute; latency is how long one driver takes to pay. A booth can be fast per car yet still have a long queue if only one booth is open.

The catch on Day 1: you set the throughput, not the server.

1 VU x (246ms request + 1000ms sleep)  =  ~0.8 requests/sec
  • Remove sleep(1) and throughput jumps to roughly 4/s.
  • Add 10 VUs and it jumps to roughly 8/s.
  • The server was never the limit — it was idle throughout.

The moment this flips is when the load exceeds what the server can handle. Throughput then stops rising no matter how many VUs you add — it flattens. That ceiling is the system's real capacity, and finding it is the point of a breakpoint test.

11. Understanding expected_response:true

It means one thing only: the server replied with a success status code (200–399). It has nothing to do with your own checks or conditions.

The indented line in the summary is the same duration metric, filtered to successful requests only.

Worked example – why k6 bothers to split them

RequestResultTime
1200 OK1000ms
2200 OK1000ms
3500 Error10ms
4500 Error10ms
http_req_duration ..............: avg=505ms    <-- all 4 requests
  { expected_response:true }....: avg=1000ms   <-- only the 2 that worked
  • 505ms is a lie — the errors returned in 10ms and dragged the average down.
  • 1000ms is the truth — when the server actually did its job, it took a full second.

That second line exists so that fast failures cannot make a system look fast. If the two lines differ, trust the second one for latency and go find out why requests are failing.

12. Understanding http_req_failed – and the false-green trap

  • It is a rate, not a count: 0.00%, 0 out of 24.
  • “Failed” means the status code was not 2xx/3xx. It does not mean k6 could not run the request.
  • A 500 counts as failed. A timeout counts as failed.
The trap: a request returning 200 OK with an error message in the body counts as a SUCCESS here.

http_req_failed: 0% does not mean your test did the right thing.

Real example: the old hand-written Scenario2.js had a dead session cookie, so every call redirected to the login page, which returned 200. The report was fully green while the test did nothing at all.

http_req_failed answers “did HTTP work?” — not “did the business action work?”. Catching the second one is the job of check() (Day 4).

13. What a smoke test proves – and what it does not

It PROVEDIt did NOT prove
  • The script runs and the endpoint is reachable.
  • TLS works and connection reuse works.
  • A single-user baseline of ~246ms — the best the system can possibly do with zero competition.
  • Anything about concurrency. One user never queues or contends for resources.
  • Anything about stability over time. 30 seconds cannot reveal a memory leak.
  • Anything about recovery after a spike or failure.
  • That the response was correct — there were no checks on the body.
  • Anything about the real product — this was a public demo site, not MainManager.

Why the baseline matters: when p95 later reads 3s at 100 VUs, the 246ms baseline tells you the system degraded 12 times over. Without a baseline, “3 seconds” is a number with no meaning.

Summary of a smoke test: it proves the instrument works, not that the patient is healthy. That is precisely why you run it first — every minute spent debugging a broken script during a 250-VU run is a wasted test window.

TermMeaning
