Day 3 – The k6 Script Lifecycle

Learning notes · Scripts: day3-lifecycle.js, day3-journey.js

1. The four stages – and how often each runs

StageWhere it livesHow often it runs
1. initTop level of the file, outside any functionOnce per context — more times than you have VUs
2. setupexport function setup()Exactly once for the whole test
3. VU codeexport default function ()Every iteration — potentially thousands of times
4. teardownexport function teardown()Exactly once, at the very end

With 10 VUs and 24 iterations each:

init      ->  ~12 times   (unpredictable - see section 3)
setup     ->    1 time
default   ->  240 times   <-- anything expensive here is multiplied by 240
teardown  ->    1 time

2. Why this is the highest-stakes concept so far

Putting the right code in the wrong stage is the number one way people break their own load test.

Real example from the MainManager framework: login was inside the VU function, so every iteration logged in again.
Symptoms: 80%+ http_req_failed, "login page 200" failing ~98%, an absurd iteration count.
Fix: ensureSession() — log in once and reuse the session.

The load test was not measuring the product; it was hammering the login door.
The rule that prevents it. Ask of every line: “should a real user do this ONCE, or EVERY time?”
Once → setup(). Every time → VU code.

3. The surprise: init ran 6 times, not 2

Test script: vus: 2, one console.log('>>> INIT') at the top level. Predicted 2 prints. Actual output showed 6.

[0000] INIT   <-- 1: k6 loads the script to discover `options` and the exported functions
[0000] INIT   <-- 2: a context for setup() to run in
[0000] INIT   <-- 3: VU 1's own context
[0000] INIT   <-- 4: VU 2's own context
[0011] INIT   <-- 5: a context for teardown() to run in
[0011] INIT   <-- 6: one more at shutdown

k6 needs a fresh JavaScript environment for every context it creates — not only VUs, but also the one that reads your options and the ones that run setup() and teardown().

Do not memorise 6. Memorise the rule: init runs an unpredictable number of times, always more than your VU count — so it must be cheap and free of side effects.

What belongs where

Belongs in initNever in init
  • import statements
  • open() to read a CSV or file — only legal here
  • Building a SharedArray
  • Constants and configuration
  • HTTP requests (k6 forbids them here)
  • Creating records, writing files
  • Anything slow
  • Anything that must happen exactly once
Proof of the danger, from the real output: two INIT lines appeared at [0011] — eleven seconds in, AFTER the test body had finished. If init code created a database record you would now have 6 records, two of them created after the test ended. If it logged in, that is 6 unwanted logins.

4. The other trap the output revealed: __ITER is per-VU

>>> VU 1 iteration 0        >>> VU 2 iteration 0
>>> VU 1 iteration 1        >>> VU 2 iteration 1
...
>>> VU 1 iteration 7        >>> VU 2 iteration 7

Both VUs counted 0 to 7 independently. There is no global iteration counter.

This directly affects the Day 2 script:

if (__ITER % 10 === 0) { /* the slow request */ }
  • At 1 VU it fired on iterations 0, 10, 20 — exactly 1 in 10, as designed.
  • At 50 VUs all 50 VUs would fire it simultaneously on their own iteration 0, then together again on iteration 10.
  • Result: synchronised bursts, not a steady 10% trickle. The script worked only because it used 1 VU.

Genuine randomness needs Math.random(), or separate scenarios in the config.

5. The setup() data channel

export function setup() {
  return { token: 'fake-token-123' };   // <-- returned here
}

export default function (data) {        // <-- arrives here every iteration
  ... data.token ...
}

export function teardown(data) {        // <-- and here too
}

Confirmed live — the teardown log printed token was fake-token-123. The full path works: setup() → every iteration → teardown().

  • This is the official channel for “do the expensive thing once, share the result”: fetch an auth token, create test records, look up IDs.
  • Constraint: the data is copied to each VU, not shared. A VU can read it but cannot write back in a way other VUs can see. VUs are isolated by design.

6. Multi-request iterations

Every earlier script made one request per iteration, so iterations and http_reqs were identical. A 3-request journey breaks that:

iterations ..........: 8      0.252139/s
http_reqs ...........: 24     0.756417/s
iteration_duration ..: med=3.88s

8 iterations x 3 requests = 24 http_reqs      confirmed

Two throughputs now exist – always say which one you mean

0.252 journeys/sec    <-- iterations/s
0.756 requests/sec    <-- http_reqs/s

Same test. Quote the wrong one and you misstate your load by 3x.

7. The blended-metric problem

A 3-endpoint journey produced ONE latency metric:

http_req_duration: min=238ms  med=272ms  p95=331ms  max=336ms
  • These are not a fast path plus a tail — they are three different endpoints averaged together.
  • p95 = 331ms is almost certainly the slowest endpoint's normal speed, not a tail.
  • avg (284) > med (272) fires the tail alarm, but the cause is an uneven mix, not slow requests.
  • The summary cannot tell you WHICH endpoint is slow, so nothing can be fixed and no SLA can be set.

The fix – tags (full lesson later):

http.get('https://quickpizza.grafana.com/',           { tags: { name: 'homepage' } });
http.get('https://quickpizza.grafana.com/api/quotes', { tags: { name: 'quotes' } });
http.get('https://quickpizza.grafana.com/api/names',  { tags: { name: 'names' } });

=>  http_req_duration{name:homepage} .. p95=331ms   <-- the slow one
    http_req_duration{name:quotes} .... p95=245ms
    http_req_duration{name:names} ..... p95=250ms
Principle: one number per thing you care about. A metric blended across different operations is unactionable no matter how many percentiles you print.

8. The broken-script signature – memorise this

A missing import http from 'k6/http'; produced ReferenceError: http is not defined, and this summary:

iteration_duration ..: avg=16.02us           <-- MICROSECONDS
iterations ..........: 6882  4803/s          <-- 4,803 per second
data_sent ...........: 0 B                   <-- nothing was ever sent
http_req_* ..........: (completely absent)   <-- no HTTP metrics at all

The script threw on the first line, so each iteration ended in microseconds and k6 span the loop 6,882 times in 1.4 seconds.

SignalHealthyBroken
iteration_durationsecondsmicroseconds
iterations/ssingle or double digitsthousands
data_sentsome bytes0 B
http_req_*presentmissing entirely
This is the same signature as the MainManager 250-VU collapse ("8842 tight-loop iterations, 60% http_failed").

An absurd iteration count with a microsecond iteration_duration never means great performance — it means the script is failing fast.

Reflex: if iterations looks impossibly high, do not read the latency numbers at all. Scroll up and find the error.

Classifying k6 failures at a glance

ErrorCause
moduleSpecifier couldn't be foundWrong path or the file does not exist. Check both.
ReferenceError: X is not definedMissing import. Produces the tight-loop signature above.
Error naming a line numberSyntax problem in the script.
Errors appearing after VU startupRuntime problem — the script parsed but failed while running.

9. The sizing workflow – closing the loop

Question: how do we know a request takes 0.25s? Answer: we do not. We measure it.

1. Write the script
2. Run it at 1 VU for 30s          <-- the smoke test
3. Read iteration_duration (med)   <-- your one input; ignore the parts
4. Do the sizing maths
5. Run the real load test
6. Compare predicted vs actual throughput
Use med, not avg — avg is skewed by one slow iteration; med gives the typical journey.
Measure at 1 VU on an idle server. Measuring under load gives an inflated figure that the load itself caused.

Worked example with real measured numbers

measured:   iteration_duration med = 2.55s, 2 requests per iteration

1. throughput   =  1 VU / 2.55s        =  0.392 journeys/s   (k6: 0.383)
                                       =  0.78 req/s         (k6: 0.766)
2. iterations   =  30s / 2.55s         =  11.7 -> 12          (k6: 12)
3. http_reqs    =  12 x 2              =  24                  (k6: 24)
4. VUs for 20 req/s:
      20 req/s / 2 requests per journey  =  10 journeys/s
      10 x 2.55s                         =  ~26 VUs

Which of the four do you actually calculate by hand?

Calculationk6 reports it?Manual?
ThroughputYesNo
Total iterationsYesNo
Total requestsYesNo
VUs to reach a targetNeverYes

k6 only reports what already happened. “How many VUs do I configure?” must be answered before the run, so only that one is genuinely manual. The other three are useful as a sanity check:

Predicted vs actualMeaning
Roughly equalTest behaved as designed
Far fewer iterationsThe server slowed down — that is a finding
Absurdly moreScript is erroring in a tight loop

The unit-conversion trap

journeys/s  =  requests/s  /  requests per iteration        <-- DO THIS FIRST
VUs         =  journeys/s  x  iteration_duration

Example: 10 APIs per journey, 4s journey, target 20 req/s.

correct:   20 / 10 = 2 journeys/s;  2 x 4 = 8 VUs
skipped:   20 x 4              = 80 VUs      <-- 10x too much load

10. Where the target comes from

A made-up target produces a made-up verdict. Real sources:

SourceHow you get the number
Production logs / APMBest. Count requests during peak hour, divide by 3600.
Business requirement“must support 500 concurrent users at month-end”
Existing SLAAlready agreed with the customer
Growth projectionToday's peak x expected growth

The caveat to state out loud when reporting

The VU count came from an idle-server measurement. Under real load journeys get slower, so a run sized for 20 req/s may only achieve 15.

That is not a mistake — that is the finding. The system could not sustain the target.
ApproachBehaviour
Fixed VUs (constant-vus)Load falls as the server slows. Report the shortfall as evidence.
Arrival rate (constant-arrival-rate)k6 forces the target rate regardless, adding VUs as needed. Closer to real traffic — use this for capacity work.
