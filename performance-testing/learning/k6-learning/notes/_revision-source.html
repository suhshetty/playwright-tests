Gap 2 — Sizing, as two questions

Q1: How many JOURNEYS per second?  =  target req/s  /  requests per journey
Q2: How long is one journey?       =  iteration_duration (med, from a 1-VU smoke test)

              multiply them   ->   VUs

Worked example

Given:  4 requests per journey, iteration_duration med = 2s, target 40 req/s

Step 1:  40 / 4  = 10 journeys/sec        <-- the step everyone skips
Step 2:  10 x 2  = 20 VUs

preAllocatedVUs: 20        (the calculation)
maxVUs:          60-100    (3-5x, headroom so k6 can compensate)

Always check forwards

20 VUs / 2s = 10 journeys/s  x 4 requests = 40 req/s      target met

Forgot to divide by 4?  ->  80 VUs  ->  forward check gives 160 req/s  ->  obviously wrong
RuleWhy
Use med, not avgavg is skewed by one slow iteration
Measure at 1 VU on an idle serverMeasuring under load gives an inflated figure the load itself caused

Gap 4 — Where code goes (lifecycle)

Ask of every line: “would a real user do this ONCE, or EVERY TIME?”
StageRunsPut this here
initMANY times (6 observed with 2 VUs)import, constants, open() a CSV (only legal here), SharedArray
setup()ONCE per testLog in and return a token; create test data; look up IDs

export function setup() {
  const token = login();        // happens ONCE
  return { token };
}

export default function (data) {
  useSession(data.token);        // every VU receives a COPY
}
Never do thisWhy
HTTP in initForbidden by k6, and init runs many times
Anything with side effects in init6 contexts = 6 records created, some AFTER the test ends
Login in VU codeThe login-flood bug — 80%+ failures, the test hammers the login door instead of measuring the product
__ITER to shape a workloadIt is PER-VU and starts at 0, so every new VU repeats the branch. Use Math.random().
A second options block inside a functionoptions is top-level and declared ONCE

Caveat on setup() data: it is COPIED to each VU, not shared. A VU can read it but cannot write back in a way others see.

Gap 5 — The report, 5 slots

1. VERDICT   pass/fail vs the target        <-- FIRST, always
2. NUMBER    p95 + the target
3. HUMANS    % of USERS affected (not requests)
4. WHERE     which endpoint or feature
5. ASK       what you want someone to do
Never lead with the good news.

Before and after

BAD:  "Performance was okay. Average response time was 1.2 seconds
       and no requests failed."

  "okay"               -> vague, leads with good news
  "average 1.2s"       -> avg describes nobody, hides the tail
  "no requests failed" -> http_req_failed, the false-green metric
  (missing)            -> no target, no impact, no ask
GOOD: "We're failing the 3-second target. p95 is 8.2 seconds - roughly
       1 in 10 requests takes over 8s while the rest return in 0.25s,
       so about 65% of user sessions hit at least one stall. It's
       isolated to the work-order grid. I need a backend engineer to
       profile that call."

The requests-to-users conversion (slot 3)

users affected  =  1 - (1 - p)^requests per session

10% slow requests, 10-request session:   1 - 0.9^10  =  65% of users

“x% of requests” is a technical fact. “y% of users” is the business impact — always the bigger, more persuasive number.

Bonus — the question that was missed

The 4 questions every performance test answers:

1. Is it fast enough?             <-- MISSED. The most common one by far.
2. How much can it take?
3. Does it stay healthy over time?
4. Does it recover?

Say which one you are answering before writing a line of code. Most poor perf work skips this and produces a test that answers nothing.
