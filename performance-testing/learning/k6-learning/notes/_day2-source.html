Day 2 – VUs, Throughput, Percentiles and Honest Reporting

Learning notes · Scripts: day2-throughput.js, day2-avg-lies.js

1. The sentence that means almost nothing

You will hear this constantly: “We tested with 100 users.” It is nearly meaningless. Three tests, all with “100 users”:

TestVUsThink timeThroughput
A100sleep(30)~3 requests/sec
B100sleep(1)~80 requests/sec
C100none~400 requests/sec

Same 100 VUs. A 130-times difference in actual load. Test A is a sleepy afternoon; Test C is close to a denial-of-service attack.

What actually describes a load test: throughput (requests/sec) plus the shape of the traffic. VU count is an implementation detail, not a description of load.

2. The formula that explains everything

throughput  =  VUs  ÷  iteration_duration

Checked against the real Day 1 run:

1 VU ÷ 1.246s  =  0.80 req/s        k6 reported 0.786/s   correct

Three variables. Change any one and throughput moves. This single formula lets you predict the load of a test before running it.

Related counting rules

RuleDetail
iterations is the TOTAL across all VUsNot per VU. 10 VUs doing 24 loops each = 240 reported iterations.
total http_reqs = iterations × requests per iterationIf one iteration makes 3 requests, 240 iterations = 720 requests.
Self-check your maths two waysthroughput × duration should equal your iteration estimate. 8.025 × 30 = 240. If the two routes disagree, you have misunderstood the test.

This matters in real work: one MainManager iteration fires dozens of HTTP calls, so a run shows a few thousand iterations but hundreds of thousands of http_reqs. When reporting, say which you mean — “240 user journeys” and “720 requests” are both true and sound very different.

3. Exercise 1 – predict, then measure

import http from 'k6/http';
import { sleep } from 'k6';

export const options = {
  vus: __ENV.MYVUS ? parseInt(__ENV.MYVUS) : 1,
  duration: '30s',
};

export default function () {
  http.get('https://quickpizza.grafana.com/');
  if (__ENV.NOSLEEP !== 'true') {
    sleep(1);
  }
}

__ENV.X reads a value passed on the command line with -e X=value, so the same file can be run three different ways without editing it.

Results

RunPredictedActualVerdict
A — 1 VU, sleep(1)0.80/s, 24 iters0.774/s, 24 itersCorrect
B — 1 VU, no sleep4.07/s, 122 iters3.63/s, 109 iters11% low — see below
C — 10 VUs, sleep(1)8.03/s, 240 iters7.64/s, 239 itersCorrect to 0.4%

Why Run B missed – the model was right, the input was stale

input used:            246ms  (yesterday's measurement)
actual duration avg:   267.77ms
actual iteration avg:  275.42ms

recompute:  30s ÷ 0.275s = 109 iterations   <-- exactly what was measured
When a prediction misses, ask which part was wrong — the formula or the assumption? Here the formula was perfect and the assumed latency was out of date.

Baseline drift – a professional habit

  • Day 1, Run A: 246ms. Day 2, same script, same endpoint: 257ms. A 4% difference for no reason at all.
  • Causes: network conditions, server load, time of day.
  • Always re-measure your baseline in the same session as the comparison. Comparing today's 250-VU run against last week's baseline is how people invent regressions that do not exist.

4. VUs are not users

A VU is a loop, not a person. The difference is critical:

When the server slows downA real userA virtual user
What they doStill arrives and joins the queueWaits politely and slows down
Effect on loadQueue grows, arrival rate stays constantLoad automatically drops
The closed-model trap: with fixed VUs, when the server gets slower your test applies less load. The system is drowning and your test responds by easing off — so it never reaches the real breaking point. 
Server healthy:      1 VU ÷ 1.25s = 0.80 req/s
Server struggling:   1 VU ÷ 6.00s = 0.17 req/s   <-- load dropped 79%

This is closed model (fixed VUs) versus open model (fixed arrival rate). Day 5 covers the executors that fix it.

5. Adding load does not automatically add latency

Run C increased load ten-fold. The prediction was “latency will get slower”. What actually happened:

Run A (1 VU,   0.77 req/s):  http_req_duration avg = 257.41ms
Run C (10 VUs, 7.64 req/s):  http_req_duration avg = 258.22ms
                                                      ^
                                    10x the load, 0.8ms difference

Latency was flat. Because 8 requests/sec is nothing for that server — nobody queued, so nobody waited.

Queueing only causes slowdown once a resource is saturated. Ten people entering a supermarket with twenty open tills are all served instantly. The same ten entering a shop with one till start forming a line.

The most important shape in performance testing

latency
  ^
  |                                       ___/   <-- the "knee": capacity exceeded,
  |                                    __/           queues form, latency explodes
  |________________________________ __/
  |   flat - server has spare capacity
  +-------------------------------------------> throughput
      you are HERE (8 req/s)         ^
                                  the knee

Finding where the knee sits is what a breakpoint test does, and it is the number that actually answers “how many users can we support?”

6. Exercise 2 – making avg lie to you

import http from 'k6/http';
import { sleep } from 'k6';

export const options = {
  vus: 1,
  duration: '60s',
  summaryTrendStats: ['min', 'med', 'avg', 'p(90)', 'p(95)', 'p(99)', 'max'],
};

export default function () {
  if (__ITER % 10 === 0) {
    http.get('https://quickpizza.grafana.com/api/delay/8');
  } else {
    http.get('https://quickpizza.grafana.com/');
  }
  sleep(1);
}
ElementWhat it does
__ITERBuilt-in counter: which loop number am I on? Starts at 0.
__ITER % 10 === 0True on iterations 0, 10, 20… so 1 in every 10 requests is slow.
/api/delay/8Server deliberately waits 8 seconds before replying.
summaryTrendStatsAdds p(99) to the printed summary — k6's default list leaves it out.

Results – all four predictions correct

StatisticPredictedActualReads as
med~257ms256.34ms“a quarter of a second, excellent”
avg~1s1.11s“about a second, acceptable”
p(95)~8s8.25s“1 in 10 users waits over 8 SECONDS”
max~8s8.25sthe worst single request

The arithmetic worked out exactly:

25 fast x 0.256s =  6.40
 3 slow x 8.250s = 24.75
                   -----
                   31.15  ÷ 28 = 1.112s      k6 reported 1.11s
Why avg is the worst possible number here: it did not simply mislead — it split the difference. 1.1 seconds is slow enough to look mediocre but fast enough that nobody panics. A manager files it and moves on. That is exactly how a serious problem survives.

7. How percentiles are really calculated

position = percentage x total number of requests

Example with 100 requests, 90 fast and 10 slow, sorted fastest to slowest:

position:  1 ........................... 90 | 91 ............ 100
value:     257ms ..................... 257ms | 8000ms ..... 8000ms
           |-------- the 90 fast ones ------| |-- the 10 slow --|
StatisticPosition = % x 100Value thereVerdict
med (p50)50257mslooks fine
p(90)90257mslooks fine
p(95)958000msfinds the problem
max1008000mssomething is very slow

A percentile is a single value at a position — not a group of requests. It is a boundary line: p(95) = 8000ms means “95% of requests were 8000ms or faster”.

The consequence: a percentile can MISS a problem

Different example — 95 requests at 2s and 5 requests at 10s:

StatisticPositionValueWhat it tells you
med502snothing wrong
p(90)902snothing wrong
p(95)952snothing wrong — the 10s requests are invisible
p(99)9910sfound it
max10010ssomething is very slow
The rule: a percentile only sees a problem if the problem is bigger than the slice above that line.

p95 sees problems affecting more than 5% of requests. p99 sees problems affecting more than 1%.
If this share of requests is slowWhich percentile catches it
20%p90, p95, p99 all catch it
10%p95 and p99 catch it; p90 sits on the edge
2%only p99 catches it
0.5%you need p99.9

Never report a single percentile. Report the shape:

p50 =  2s
p95 =  2s
p99 = 10s
max = 10s

Reads as: "most requests are 2s, but 1-5% of users hit 10 seconds."

This is why the MainManager reports showing p99 = NaN are a real gap — they are currently blind to any problem affecting less than 5% of requests.

8. Bimodal distributions break percentile intuition

The run reported p(90) = 2.65s. No request in the entire run took 2.65 seconds. Every one was either ~256ms or ~8250ms.

25 fast requests          3 slow requests
[....................]    [...]
                     ^
                p(90) lands HERE, in the gap - so k6 interpolates
                and invents a number nothing actually measured
  • A system with two distinct behaviours (fast path / slow path) has a bimodal distribution.
  • Real causes: cache hit vs cache miss, in-memory vs database, small dataset vs large.
  • Percentiles that land in the gap produce meaningless numbers.

How to handle it: report the two populations separately (via tags), or report the proportion: “10% of requests take 8s, 90% take 0.25s.” That sentence beats any percentile.

9. How to catch a hidden tail – five tools

Clue 1: avg bigger than med (free, always available)

med = 256ms
avg = 1.11s     <-- 4.3x the median
ComparisonMeaning
avg approx equal to medUniform, no tail. (Day 1: 246.37 vs 246.38.)
avg > medA tail exists — go hunting.
avg much greater than medA serious tail. Some users are suffering badly.

If avg exceeds med, something in the tail is dragging the average up. There is no other explanation.

Clue 2: max

Proves at least one request was that slow. It cannot tell you whether that is 1 request or 500, but you cannot unsee the ceiling.

Tool 1: add p(99) to the output

summaryTrendStats: ['min', 'med', 'avg', 'p(90)', 'p(95)', 'p(99)', 'max'],

Tool 2: thresholds – fail the test automatically

thresholds: {
  'http_req_duration': ['p(99)<3000'],
},

k6 now fails the run if p99 exceeds 3 seconds. You cannot miss it. (Day 4.)

Tool 3: tags – find WHICH request is slow

Percentiles say that something is slow, never what. Tagging measures each endpoint separately:

http_req_duration{endpoint:homepage} ..: p(95)=200ms   <-- fine
http_req_duration{endpoint:search} ....: p(95)=10s     <-- the culprit

(Day 10.)

Tool 4: time-series graphs – why Grafana exists

Every statistic above is a single number for the whole run. It cannot distinguish these two situations:

Case A - random scatter:
  10s   .      .        .       .        .      .
   2s  ########################################
      |------------------- time -----------------|
      Occasional slow requests. Annoying, low priority.

Case B - a cliff:
  10s                          #################
   2s  ######################
      |------------------- time -----------------|
      Something BROKE at that moment. Urgent.

Identical avg, p99 and max. Completely different problems. Case A is a tuning task; Case B means a resource ran out mid-test — a connection pool filled, memory hit a limit, a cache expired. Only a time-series graph shows the difference.

10. The closed-model trap, proven with real data

Compare throughput between the two Day 2 exercises:

Run A  (fast server):        0.774 req/s
avg-lies run (10% slow):     0.467 req/s     <-- 40% LESS load

Verify where the time went:

25 fast iterations x 1.25s = 31.25s
 3 slow iterations x 9.25s = 27.75s
                             ------
                             59.0s  = the 60s duration
The VU spent nearly half the test sitting still, waiting for slow responses instead of generating traffic. The server got slower, so the test applied less load.

Real users do not behave this way — they keep arriving whether the server copes or not. A struggling system needs MORE pressure to reveal its limits, and a closed-model test gives it less. This is why capacity tests use arrival-rate executors instead of fixed VUs.

One more confirmation from the same run:

http_req_duration: avg=1.11s
http_req_waiting:  avg=1.11s     <-- identical

The delay is entirely server thinking time — correct, because /api/delay/8 is literally the server sleeping. Not the network, not the test machine. Day 1's diagnostic skill applied.

11. Requests are not users – the conversion that changes the story

The run had 10% of requests slow. But a real user session makes many requests. Say 10.

What is the chance a user completes a session without hitting a single slow request?

0.9 x 0.9 x 0.9 ... (10 times) = 0.9^10 = 0.35

So only 35% escape.  =>  65% of USERS hit at least one 8-second wait.
Requests per sessionUsers who hit at least one slow request
110%
541%
1065%
2088%
The rule: “x% of requests are slow” is a technical fact. “y% of users hit it” is the business impact — and it is always the bigger, more persuasive number. Convert before you report.

This matters enormously in real work: a MainManager session is login + module load + grid + filters + modal — dozens of requests. Even a 2% slow-request rate there means nearly every user hits a stall.

12. How to report to a manager

A weak sentence: “95% of users are working fine during load.”

ProblemWhy it fails
Leads with the good newsThe manager hears “working fine” and stops listening. You bury your own finding.
Omits the magnitude“Some are slow” is unactionable. “8 seconds” is actionable.
Asks for nothingA finding with no requested action is just trivia.

The 5-part structure of a proper performance statement

  1. Verdict against the target — pass or fail, stated first
  2. The number and the target — p95, and what it should be
  3. Who is affected, in human terms — not “5% of requests” but “1 in 20 users”
  4. Which feature — where to look
  5. What you want — the ask
Applied: “We're failing our 3-second target. p95 response time is 8.25 seconds — about 1 in 10 requests takes over 8 seconds while the rest come back in a quarter of a second. It's isolated to the [X] endpoint. I need a backend engineer to profile that call.”

Same data. Impossible to file and forget.

13. Two small operational notes

ObservationExplanation
vus: 3, min=3, max=10k6 samples “how many VUs are busy right now?” once a second. Near the end most VUs had finished, so the last sample saw 3. It does not mean only 3 VUs ran — 239 iterations prove all 10 worked. Trust vus_max.
Hundreds of progress linesCosmetic only. k6 normally rewrites one line in place; sometimes it prints a new line each time. Silence it with --quiet.

15. Glossary additions

TermMeaning
ThroughputRequests completed per second. The real measure of applied load.
Closed modelFixed number of VUs. Load falls automatically when the server slows.
Open modelFixed arrival rate. New requests keep arriving regardless of server health — like real traffic.
The kneeThe throughput at which latency stops being flat and starts climbing. The system's practical capacity.
Bimodal distributionTwo distinct groups of response times (e.g. cache hit vs miss). Breaks single-percentile reporting.
TailThe slowest requests in a run. Where real user pain lives.
