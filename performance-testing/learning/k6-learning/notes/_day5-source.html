Day 5 – Load Shapes, Closed vs Open Model, Executors

Learning notes · Scripts: day5-stages.js, day5-arrival.js

1. The two families

CLOSED model  ->  you control the VUs    ->  "how many users?"
OPEN model    ->  you control the RATE   ->  "how many requests per second?"
The closed-model trap (proven with real data on Day 2): with fixed VUs, when the server slows down each VU waits longer, so the test applies LESS load.

Real users keep arriving regardless of server health. A struggling system needs MORE pressure to reveal its limits, and a closed-model test gives it less.

2. Load shape 1 – stages (ramping VUs)

export const options = {
  stages: [
    { duration: '10s', target: 5 },   // ramp 0 -> 5 VUs
    { duration: '20s', target: 5 },   // hold at 5
    { duration: '10s', target: 0 },   // ramp down
  ],
};

Why ramp rather than jump straight to target

ReasonDetail
Caches warm upA cold start makes the first seconds look artificially terrible
Connection pools growServers scale gradually, not instantly
RealisticReal traffic ramps; it does not teleport
Ramp-DOWN matters tooIt is how you see whether the system recovers

Counting a ramped load: the AREA formula

total iterations  =  area under the VU curve  ÷  iteration_duration
area = (1/2 x 10 x 5)  +  (20 x 5)  +  (1/2 x 10 x 5)
     =       25         +    100     +       25        =  150 VU-seconds

150 ÷ 1.23s = ~122 iterations        ACTUAL: 125
ApproachResultVerdict
Area under the curve~122Correct (actual 125)
duration ÷ iter × VUs = 40/1.25×516028% too high — treats ramps as full load
A ramp delivers HALF the load of a hold at the same target (a triangle is half a rectangle).

The simple duration ÷ iteration_duration × VUs formula is just the special case where VUs are constant, i.e. where the area is a plain rectangle.

Trap: a ramping run's reported throughput is NOT your test load

http_reqs: 125    3.055943/s        <-- AVERAGE across the whole run, ramps included

at the 5-VU plateau:  5 ÷ 1.23  =  4.07 req/s     <-- the actual test load
If you reportYou are saying
3.06 req/s“we tested at 3 req/s” — understates by 25%
4.07 req/s“we sustained 4 req/s at peak” — the honest figure

Quote the plateau, not the average. And note the summary cannot show you where the plateau was — that needs a time-series graph. This is one of the main reasons Week 3 exists.

Also expect blocked/duration spikes during ramp-up: each newly created VU opens its own connection and pays its own TLS handshake. Exclude the ramp from reported numbers.

3. Load shape 2 – arrival rate (the open model)

export const options = {
  scenarios: {
    steady_load: {
      executor: 'constant-arrival-rate',
      rate: 5,                 // 5 iterations...
      timeUnit: '1s',          // ...per second, regardless of server health
      duration: '30s',
      preAllocatedVUs: 10,     // workers ready at the start
      maxVUs: 50,              // may recruit up to 50 if needed
    },
  },
};
constant-vusconstant-arrival-rate
VUs are fixedRATE is fixed
Throughput sags when the server slowsk6 ADDS VUs to defend the rate
No signal that load was missedReports dropped_iterations if it cannot keep up

Setting the parameters

ParameterHow to choose it
rate + timeUnitFrom the business target (Day 22). Convert requests/s to iterations/s first.
preAllocatedVUsrate × iteration_duration — your sizing calculation
maxVUs3–5× preAllocatedVUs — headroom so k6 can compensate when the server slows
Set maxVUs equal to your calculation and you cap k6's ability to defend the rate — which defeats the point of the open model.

The three diagnostic states

ObservationMeaning
VUs stay near preAllocatedVUs, rate holdsSystem is healthy
VUs climbing toward maxVUs, rate still holdsSystem is degrading — k6 is compensating. An early warning BEFORE latency thresholds fire. No closed-model test can show this.
dropped_iterations > 0Capacity exceeded — k6 could not deliver the load you asked for

4. The measured result – the open model works

Same 10%-slow workload, same slow server:

Day 2, fixed VUs:      0.467 iterations/s
Day 5, arrival-rate:   4.130 iterations/s     <-- 8.8x the load

And the accounting is exact:

requested:  5/s x 30s  =  150 iterations
delivered:                129
dropped:                   22
                          ---
                          151
dropped_iterations is k6 saying: “you asked for 5/s and I could only deliver 4.13/s.” That is a capacity finding no closed-model test can produce.

5. The accidental discovery – the __ITER cascade

Prediction: ~11 VUs needed. Actual: k6 recruited 32. Investigating why produced the most valuable lesson of the day.

Step 1 – the real proportion of slow requests was 25%, not 10%

Derive it from the measured average:

if x = fraction slow:   8.25x + 0.245(1 - x) = 2.22   (the measured avg)
                                          x  = 0.247   ->  ~25% slow

Step 2 – where 25% came from

if (__ITER % 10 === 0) { /* the slow request */ }
__ITER is per-VU, and it starts at 0. Since 0 % 10 === 0, every newly created VU hits the 8-second endpoint on its VERY FIRST iteration. 
32 VUs created  ->  32 "iteration 0" slow requests
32 ÷ 129 total  =  24.8% slow        matches the 24.7% derived from avg

Two independent calculations agreeing to one decimal place. That is the explanation confirmed.

Step 3 – the cascade that demanded 32 VUs

1. k6 starts 10 VUs
2. ALL 10 immediately block for 9.25s (their iteration 0 is slow)
3. No free worker -> k6 recruits more VUs
4. Each NEW VU also blocks instantly on its own iteration 0
5. Repeat -> 32 VUs, and 22 iterations still missed their slot

Every worker k6 hired was useless the moment it arrived.

The rule

__ITER-based logic  +  auto-scaling VUs  =  a workload you did not intend

The script was not modelling “10% of requests are slow”. It was modelling “every new user's first action is slow” — a completely different system.

Never use __ITER to shape a workload when the VU count can change. Use randomness instead: 
if (Math.random() < 0.1) { /* genuinely 10%, VU-count independent */ }

Two confirmations from the same run

ObservationLesson it confirms
avg=2.22s med=245.8ms p90=8.24s p95=8.25sTextbook bimodal — med is the fast path, p90/p95 the slow path, and avg describes nothing that actually happened (Day 2)
duration 2.22s == waiting 2.22sEntirely server-side, even at 32 VUs. Not the test machine (Day 1)

6. The 6 executors

ExecutorYou fixReach for it when
constant-vusVUs + durationSteady baseline; smoke tests
ramping-vusstages (VU targets)Warm-up, gradual load, VU-based breakpoints
constant-arrival-raterate + durationLoad test against a real req/s target
ramping-arrival-raterising rateCapacity tests — finding the knee
shared-iterationstotal N iterations“Process these 1,000 records” — a fixed amount of work
per-vu-iterationsN per VU“Each of 10 users does exactly 5 orders”

The decision in three questions

1. Do I have a target in requests/sec or journeys/sec?
      YES -> arrival-rate family          NO -> question 2

2. Am I looking for the breaking point?
      YES -> ramping-arrival-rate         NO -> question 3

3. Is my requirement literally "N concurrent users"?
      YES -> constant-vus / ramping-vus
      NO  -> you do not have a real target yet (see Day 22)

7. Closed model is not always wrong

Fixed VUs are correct when concurrency is genuinely bounded:

SituationWhy closed is right
50 physical kiosksThere cannot be a 51st user
20 call-centre agentsHeadcount is the hard limit
A batch client with 8 worker threadsThe client's own pool caps concurrency
Smoke testsYou want 1 VU, not a rate
The SLA is written in concurrent usersMatch the contract you have to meet

Closed is wrong when modelling open internet traffic — which is most web load testing.

8. ramping-arrival-rate – the capacity shape

{
  executor: 'ramping-arrival-rate',
  startRate: 1, timeUnit: '1s',
  preAllocatedVUs: 20,
  maxVUs: 500,
  stages: [
    { duration: '2m', target: 10 },   // <-- targets are RATES, not VUs
    { duration: '2m', target: 20 },
    { duration: '2m', target: 40 },
  ],
}
CRITICAL: in ramping-vus, target means VU count. In ramping-arrival-rate, target means requests/sec.
Same word, different unit. A common and expensive mistake.

The knee reveals itself as the point where latency climbs AND dropped_iterations begin appearing.
